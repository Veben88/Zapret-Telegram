# Sprint 0: подготовка к модернизации OMR (ноябрь 2026)

Цель — зафиксировать исходную точность и скорость распознавания на устройстве, найти узкие места и подготовить
инфраструктуру, чтобы каждое следующее улучшение проверялось цифрами. Архитектура не менялась; исправлены только
подтверждённые ошибки небольшими обратимыми изменениями (коммиты `c90902e`, `acbbe7c`, `f94a317` и этот отчёт).

## 1. Текущая архитектура

```
Импорт (PrepareScreen) ─► OmrJob (WorkManager) ─► OmrWorker
   кэш omr_cache по ключу (хеш файла + движок + страницы/поворот + выбор строк/партий + режимы)
   └─► движок: HomrOnDeviceEngine (офлайн) | ClaudeVisionEngine (ключ пользователя)
         └─► по каждой партии/строке: recognize → OmrParsed → ClaudeOmr.assemble → проект (Room) + layouts/<id>.json

HomrOnDeviceEngine
   первый запуск: подбор ускорителя энкодера (HomrModels.tune: INT8/FLOAT/FP16 × CPU/XNNPACK/NNAPI)
   по страницам, следующая готовится параллельно (prefetch):
     PageRenderer.renderForOmr (PdfRenderer сразу в ширину 1920) → toGray (ARGB → серый)
     → HomrPipeline.locate → recognizePage (одна строка) | recognizeAll (хор, партии)
   затем TokenParser.parse (+ Repairs.fixDots, Triplets.restore) и LayoutBuilder (такты и ноты на исходнике)

HomrPipeline.locate
   resize до ширины 1920 (бикубика как в Pillow) → CLAHE (как в OpenCV)
   → быстрый путь: ClassicStaffMask (тёмное, наклон, маска линеек) → StaffDetector.detect (линии → пятёрки,
     достройка четырёх линий) → systems (скобка/черта системы)
   → иначе (ничего не найдено или «точный режим»): Segnet (окна 320×320, склейка SegMerge) → наклон → detect
recognizeAll
   staffCanvas (строка 1280×256, выпрямленная по верхней линейке) → Staff2Score: энкодер → декодер
   (авторегрессия с KV-кэшем, «attention» даёт положение символа) — строки параллельно (до 4 потоков)
   → mapToPage → «8» под ключом (octaveMarkScore) → слова (Lyrics, Claude) → колонки тактов (Barlines)
Parts / ChoirAssigner — какие строки какие партии; Divisi — два голоса на строке.
```

Хранение: Room `projects` (ноты, повторы, разметка — JSON), `omr_cache` (JSON результата), файлы `layouts/<id>.json`
(`SourceLayout`: такты и ноты в долях страницы), модели в папке приложения (скачиваются один раз с проверкой SHA-256,
int8-энкодер — в APK).

## 4. Проверка SegNet

Склейка окон проверена на 9 реальных страницах (цифровые и сканы, высота 2713–2764) и 4 вырезках размером не кратным 320
(1000×777, 641×641, 319×500, 200×150 — по обеим осям и меньше окна). Эталон для полосы перекрытия — те же пиксели,
прочитанные окном, сдвинутым так, что они лежат внутри него (≥ 79 px от края).

| Способ склейки | Совпадение в полосе | Совпадение на «чернилах» | «Невозможный» класс* |
|---|---|---|---|
| A. Среднее номеров классов (было, как в homr) | 99,60 % | 94,23 % | **10 612 пикс.** |
| B. Голосование окон | 99,79 % | 96,92 % | 0 |
| C. Сумма вероятностей | 99,79 % | 96,96 % | 3 |
| **D. Самое уверенное окно (выбрано)** | **99,79 %** | **96,97 %** | **0** |
| E. Дополнение белым до кратного 320 (без перекрытия) | 99,75 % | 96,40 % | 86 |

\* класс, который не выбрало ни одно из покрывающих пиксель окон. При A на скане «Atsalums» в полосе появилось
2094 пикселя «головок нот» там, где их нет; на «Зиме» — 1841 вместо 264.

Нахождение нотоносцев на всех страницах от способа склейки не зависит (полоса — у нижнего края, обычно под последней
строкой), поэтому на быстром пути (classic) результат прежний; меняются ноты/знаки у нижнего края в точном режиме и в
резервном пути через SegNet. Память — прежняя (вне полос класс пишется сразу, суммы — только для полос). Тесты:
`SegnetMergeTest` (без модели: окна, не кратные размеры, страницы меньше окна, пустые окна, несогласие окон);
эксперимент — `SegnetMergeExperimentTest` (`HOMR_SEGMERGE`).
