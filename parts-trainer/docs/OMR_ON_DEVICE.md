# Движок «На устройстве» (homr)

Статус: **реализован**, работает полностью офлайн после однократной загрузки моделей (≈140 МБ).

## Как устроено

Исходный homr (liebharc/homr, AGPL-3.0) — ~9 тыс. строк Python на numpy/OpenCV. Andromr (aicelen/Andromr) —
Python+Kivy-обёртка над ним, не Android-библиотека. Поэтому конвейер **портирован на Kotlin** (модуль `:omr`,
чистый JVM — тестируется на компьютере), а нейросети запускаются через **ONNX Runtime** (Java API:
`onnxruntime` в тестах, `onnxruntime-android` в приложении). Все три модели homr уже опубликованы в ONNX
(релиз `onnx_checkpoints`), конвертация в LiteRT не нужна.

| Этап | Реализация |
|---|---|
| Подготовка | серый, ширина 1920 (бикубика как в Pillow), CLAHE (как в OpenCV) — совпадение с эталоном: средняя разница < 1 уровня яркости |
| Выравнивание | оценка наклона линеек по маске, поворот и повторная сегментация (для фото) |
| Поиск линеек | **по умолчанию — быстрый алгоритм без нейросети** (локальный порог, длинные тонкие горизонтальные линии, вертикальные структуры вырезаются, выравнивание по наклону); `segnet` (ONNX, окна 320×320) — запасной вариант, если ничего не найдено, и «Точный режим» в настройках |
| Нотоносцы | собственный поиск пятёрок линий по маске; системы определяются по соединительной вертикали слева; выбор строки: вокал / правая / левая рука |
| Распознавание | энкодер + декодер TrOMR (ONNX), жадное декодирование с KV-кэшем, тот же словарь токенов |
| Разбор | токены → такты (`TokenParser`): знаки, пунктир, паузы, лиги (в т.ч. через тактовую черту), репризы, вольты, аккорды (берётся верхняя нота) |

Результат — тот же `OmrParsed`, что у Claude Vision, поэтому редактор, проверка сумм тактов и раскрытие повторов общие.

## Результаты на реальных партитурах (4 PDF, 32 страницы)

| Файл | Что это | Результат |
|---|---|---|
| «Радуйся» (10 стр.) | хор S/A/T/B, векторный PDF, 3/4, 4♭, тенор с «8» | нотоносцы: все страницы верно (по 4, где есть «Solo» — по 5); стр. 1 — **129 из 129 нот совпали с Python-homr** |
| «Зима» Шнитке (5 стр.) | **скан/фото** с чёрной полосой и пальцем, переменный метр 4/4, 6/4, 5/4 | нотоносцы: все страницы `[4,4,4]`; метр восстановлен, суммы долей сходятся; сверка по картинке — ноты и паузы совпадают |
| Chilcott «Agnus Dei» (5 стр.) | зернистый скан, триоли, 3/2 и 4/4, голоса опущены в начале систем | структура `[1,1,4,4]` как на странице; суммы долей сходятся; триоли читаются |
| Chilcott «Gloria» (12 стр.) | хор **на двух строках** (SA / TB с дивизи) + фортепиано | режим «Хор на двух строках + фортепиано»: голоса разделяются, на всех проверенных страницах получают ноты, суммы долей сходятся; по картинке стр. 14 совпало |

Что пришлось доработать из-за этих файлов: поиск наклонных и изогнутых линеек по полосам с выпрямлением строки
вдоль кривой; достройка нотоносца, у которого нейросеть потеряла одну линейку (её закрыла лига); устойчивая проверка
«строки соединены слева» на сканах; **переменный метр** (в т. ч. знак размера в конце строки, который модель не читает);
определение голоса по ключу, маленькой «8» и регистру.

### Известные ограничения (по результатам этих файлов)

* **Хор на двух строках + фортепиано (Gloria)** включается переключателем на экране подготовки (автоопределить
  раскладку надёжно не удалось: признак «текст песни между строками» оказался слишком шумным). В системе из 4+ строк
  фортепиано — две нижние; в системе из 2–3 строк рояль определяется по содержанию (много аккордов из 3+ нот или очень
  низкий басовый ключ). Строка SA делится на S (верхний голос) и A (нижний), TB — на T и B.
* Дивизи делится по времени: модель пишет аккорды с разной длительностью нот; одиночная нота отдаётся свободному голосу,
  а если свободны оба — звучит в обоих (унисон). При 3–4 нотах в аккорде берутся верхняя и нижняя, средние теряются.
* В обычном режиме (по строке на голос) в аккорде берётся верхняя нота.
* Точность по нотам не измерена на «эталоне»: сверка шла с Python-homr и глазами. Сканы читаются хорошо, но ошибки
  в высоте и ритме случаются — поэтому после распознавания всегда открывается редактор.
* Ключ и «8»: «8» ищется по тёмным пикселям под ключом (порог подобран на одной партитуре).

## Скорость

Замер на ноутбуке (4 ядра, CPU), страница с 8–12 нотоносцами, установившийся режим (без первого «холодного» прогона):

| | было | стало |
|---|---|---|
| Страница в среднем | 8–11 с | **5,7–8 с** (−25…30 %) |
| Поиск линеек | 2,5–4,5 с (нейросеть, 54 окна) | **0,05–0,3 с** |
| Модель segnet в памяти (57 МБ) | всегда | только в запасном/точном режиме |
| Чтение нотоносцев (энкодер + декодер) | 0,5–0,6 с на нотоносец | без изменений: теперь это ≈ 90 % времени |

Что сделано: быстрый поиск линеек (сверка с нейросетевым на 32 страницах: структура систем совпала на 28 из 32 страниц,
итоговые ноты — на 94 %; остальное — сдвиги на одну ноту и спорные места); пропуск пустых окон и поворот карты вместо
повторной сегментации в точном режиме; на телефоне число потоков ONNX Runtime ограничивается производительными ядрами.

Что пробовали и не дало выигрыша: параллельное чтение нотоносцев (энкодер уже занимает все ядра — на 4 ядрах даже
хуже; в коде оставлено, по умолчанию 1 поток). Декодер уже квантизован разработчиками homr (int8), его скорость
упирается в чтение весов на каждом шаге.

**Возможное ускорение, требующее решения владельца:** энкодер в релизе homr — float (52 МБ). Его int8-версия (17 МБ)
на 136 нотах первой страницы дала идентичный результат и работает на 45 % быстрее (209 → 115 мс на нотоносец), но
использовать её можно только опубликовав свою копию модели (например, отдельным релизом с хешем SHA-256).

## Что упрощено относительно homr

* нет автообрезки фото на фоне стола (`autocrop`) и нелинейного выпрямления страниц (`staff_dewarping`) —
  работает наклон, но не изгиб страницы (разворот книги);
* нет объединения «фортепианных пар» в одно изображение: каждый нотоносец читается отдельно;
* нет восстановления триолей (`triplet_restoration`) и OCR заголовка;
* текст песни, как и в задании, не распознаётся.

## Проверка

Тесты `omr/src/test/.../HomrReferenceTest.kt` сверяют Kotlin с Python-homr (нужны модели:
`HOMR_MODELS=<папка> HOMR_REF=<папка с эталонами> gradle -c settings-core.gradle.kts :omr:test`; без них — пропускаются):

* чистая страница: **60 из 60 токенов совпали дословно**, 46 из 46 нот — те же высота, длительность и позиция;
* вокал + фортепиано (3 нотоносца в системе): строки «вокал» и «правая рука» прочитаны без ошибок;
* диезы/бекар, пунктир, лига через такт, пауза, реприза с 1-й/2-й вольтами: ноты, метки и порядок раскрытия повторов совпали с MusicXML-источником;
* фото: наклон 2°, шум, размытие, JPEG-60, неравномерный свет: 46 из 46 нот.

Скорость на JVM (ноутбук/сервер): ≈7 с на страницу. На телефоне ожидается заметно дольше — это нужно замерить.
Все эти тесты — на синтетических страницах (Verovio). Реальные сканы и фото проверять ещё предстоит.

* Файлы скачиваются по запросу (`HomrModelManager`) напрямую с GitHub-релиза homr, проверяются по SHA-256, лежат
  во внутренней памяти приложения. В APK их нет.
